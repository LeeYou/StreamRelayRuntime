# 产品愿景

## 1. 产品名称

**StreamRelayRuntime**

## 2. 产品使命

StreamRelayRuntime 是一个面向长连接接入、WebSocket 转发、远程控制命令分发和双向流量转发的分布式服务运行时。

系统目标是成为以下产品的通用后台基础：

- **远程设备控制平台**
- **WebSocket 转发网关**
- **Agent 管理平台**
- **实时运维控制台**
- **命令执行与审计系统**
- **流量转发与隧道服务**

## 3. 非目标

StreamRelayRuntime 不定位为：

- **游戏服务器框架**：ECS 风格思想只作为服务组合模式复用。
- **完整 SaaS 业务产品**：计费、组织管理、前端 UI 不属于运行时初始范围。
- **消息队列替代品**：可以集成 MQ，但不替代 Kafka、NATS、RabbitMQ 或 Redis Streams。
- **数据库框架**：存储访问通过 Repository 接口抽象。

## 4. 核心设计目标

- **模块化架构**：每个业务能力都必须隔离在清晰接口之后。
- **分布式部署**：开发阶段支持 all-in-one，生产阶段支持独立进程部署。
- **高并发**：Gateway 和 Relay 路径必须支持大量长连接。
- **背压感知**：慢连接不能耗尽内存，也不能阻塞健康客户端。
- **安全资源所有权**：使用 C++17 RAII 与智能指针，避免原始指针所有权。
- **接口驱动测试**：核心模块支持依赖注入与 mock 实现。
- **协议优先演进**：外部与服务间契约必须文档化、版本化。
- **运行时可观测**：请求、命令、会话、转发通道、服务实例都应可追踪。

## 5. 从旧系统继承的经验

旧 ECS 风格服务系统提供了以下有价值思想：

- **消息驱动执行**：通过 packet dispatch 和 message handler 组织逻辑。
- **服务拆分**：按 app 级进程拆分能力。
- **组件化初始化**：通过组件组合服务能力。
- **服务管理器雏形**：类似服务注册与发现。
- **all-in-one 模式**：便于本地开发与调试。

StreamRelayRuntime 会有意剔除以下耦合：

- 核心运行时不包含 `Player`、`World`、`Space`、`Teleport`、移动等游戏领域对象。
- App 拓扑不硬编码在 C++ 业务逻辑中。
- 裸指针生命周期不跨异步流程暴露。
- 全局服务定位器不作为主要依赖机制。

## 6. 主要用户故事

### 6.1 WebSocket 转发

管理控制台通过 WebSocket 连接 Gateway，选择远程设备并打开转发通道。运行时在控制台与设备 Agent 之间转发二进制帧或结构化帧，同时记录流控和审计元数据。

### 6.2 远程命令分发

操作员向目标设备提交命令。Control Service 创建命令记录，将命令路由到在线设备会话，等待 ACK，跟踪执行状态，保存审计日志，并返回最终结果。

### 6.3 设备在线管理

设备 Agent 连接 Gateway，完成认证，注册能力，保持心跳，并更新在线状态。其他服务可以查询 Device Registry 获取设备当前 Gateway 连接位置。

### 6.4 分布式服务运行

系统可以部署多个 Gateway 与 Control Service。服务实例注册自身、发布心跳，并由 Router 发现。运维人员可以观察服务健康度、队列长度、命令延迟与 Relay 吞吐。

## 7. 成功指标

- **Gateway 并发能力**：单 Gateway 稳定长连接数量。
- **命令延迟**：命令往返时间 p50/p95/p99。
- **Relay 吞吐**：单 Gateway 与单 Relay Channel 每秒字节数。
- **内存稳定性**：慢客户端和网络抖动场景下内存可控。
- **可恢复性**：Gateway 或设备重连后，会话和命令状态可预测恢复。
- **可测试性**：核心路由、会话、命令、Relay 状态机具备确定性单元测试。
